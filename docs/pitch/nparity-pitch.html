LOT 02

Value proposition

What

From the first prototype to sign-off, nParity tells the backend engineer which differences between the old and new API are regressions, with a probability and a one-line reason for each.

Why

Today the check happens once, by hand, near the end, when a regression costs the most to fix. Replay tools show what differs, not whether it was intended.

What changes

Regressions surface while the work is in flight. The engineer reviews only regressions and unsure items, and the engineering manager signs off on a short list with a probability on each item.

Today the check happens once, by hand, near the end of a migration. Replay tools show what differs, not whether the difference was intended. nParity labels each difference intended, regression or unsure, with a probability read from the model's token probabilities and a one-line reason.
LOT 03

The moment

Every change on the way to a new API raises the same question: will we break anything?

Who runs it

Backend engineer

Owns both the old and the new API. Can say in a paragraph what the change is intended to do.

Who signs off

Engineering manager

Approves the cutover. Needs a short list with a probability on each item, not a raw diff.

Not for

Implementation

Writing or running the migration. nParity shows where the differences are and where to focus.

Users: the backend engineer who must prove the new API behaves like the old one, and the engineering manager who signs off the cutover. Not in scope: writing or running the migration itself. nParity finds and ranks the differences and shows where to focus.
LOT 04

Evidence

What others found

GitHub · rewriting merges with Scientist

Most mismatches were noise: the old code timing out, and commit timestamps that differed. The rollout still took roughly 5 days of part-time work, even with a purpose-built tool.

Twitter · Diffy

Built because separating real regressions from noise by hand is very hard. Without noise filtering, one random true/false field causes false alarms on 25% of requests.

Speedscale · sold today

Sells side-by-side replay of legacy and migrated services. Its public pages say nothing about renamed endpoints or intended changes.

Our interview · 26 Nov · CSOM to Mesh

“References to the actual documentation would add confidence.” Trust comes from showing the source. Mesh was a new flow, so endpoints could not be compared: the team learned by integrating.

CSOM to Mesh: about 10 months so far, with changes on both sides. Similar moves: 3 to 6 months on average. estimate

Public prior art (GitHub Scientist, Twitter Diffy, Speedscale) shows that noise dominates manual and replay-based checks. Our own evidence of need is one interview: an engineer who moved an integration from one version of a vendor API to its successor (same vendor, new process, endpoints that cannot be paired one to one). Limits: one interview. The duration figures are anecdotal: the CSOM to Mesh move has run about 10 months so far, but changes on both sides make its own effect hard to isolate, and the 3 to 6 month average for similar moves is an estimate, not a measurement.

Appendix · How it works

Steep, strain, match, compare, taste

STEP 1 Steep

Send the same requests to the old and new API.

Requests come from the old API's OpenAPI spec and seed values.

STEP 2 Strain

Mask timestamps and generated IDs. Sort unordered lists.

Fixed rules. No model.

STEP 3 Match

Pair moved endpoints and renamed fields.

Rules first. The model handles the remaining matches.

STEP 4 Compare

Diff values and types for every JSON path.

The model never judges rounding, counts or pagination.

STEP 5 Taste

Label each difference intended, regression or unsure.

Against your intent note, with a probability.

In: two API URLs, two OpenAPI specs and an intent note.Out: a short report in the terminal or the browser
Five steps: replay, strain (fixed rules, no model), match (rules first, the model only for leftovers), compare (deterministic differ), taste (the model labels each difference against the intent note). The model does only two jobs: matching leftovers and tasting. Not built: grouping multi-call flows into one step (PRD 0005) and documentation pages as input (PRD 0006). A contract-only mode and sample-request checks are available in the CLI.
LOT 12

Appendix · Why trust it

Every verdict shows how sure it is

A real probability

Each verdict is read from the model's token probabilities, not a score the model makes up.

Higher bars where mistakes cost more

p ≥ 0.95 to accept a match. p ≥ 0.98 to accept a difference as intended. Regressions are never dismissed automatically.

Numbers stay deterministic

Rounding, counts and pagination are caught by the differ. The model never judges them.

Scored on our test APIs

On our test APIs, every run is scored against an answer key, and the score is on screen.

We tested before we built: 66 model calls for about US$0.006. Yes/no questions rejected correct renames (the model gave a correct rename a 0.17% chance), so nParity asks multiple-choice questions.

Each verdict is read from the model's token probabilities (one-token calls, top 5), not a score the model writes. Thresholds: 0.95 to accept a match, 0.98 to accept a difference as intended. A regression is never dismissed automatically. Rounding, counts and pagination are decided by the differ, not the model. A model without token probabilities falls back to vote sampling, which is labelled uncalibrated.

Appendix · Built for people and AI agents

An agent can run it, read it and act on it.

Machine-readable
  • --format json: one JSON document on stdout, errors on stderr.
  • Fixed exit codes. --fail-on regression exits 5, so an agent knows to stop and look.
Small answers
  • --compact: counts, coverage, cost and finding keys.
  • Fetch one finding with its samples, not the whole report.
Long runs
  • --detach returns a run ID at once.
  • status polls progress events.
Plan first
  • --dry-run shows the calls, seed sources and skipped endpoints.
  • No replay and no model calls.

A developer tool. The agent does the fixing. nParity says where to look.

Same CLI and engine. The README section 'CLI automation' describes: --format json (one JSON document on stdout, errors on stderr), fixed exit codes, --compact, fetching a single finding, --detach with status polling, --dry-run, and --fail-on (exit code 5, so an agent knows to stop). Status: built and in the repository, not part of the live demo. It is a developer tool, not a CI build step.

LOT 15

Appendix · When it pays off

Run nParity before and during the migration

Before

Scope the change

Run the old API against an early prototype. See what will differ before you commit to a plan. Use the result to write the intent note.

During

Catch drift early, then sign off

Re-run it as the new API takes shape. A regression shows up at the next run, while it is cheap to fix. Before cutover, hand the manager a short list with a probability on every item.

Same engine, same report, from the first prototype to the cutover.

The value comes from asking early and often, not once at the end: 'will we break anything?' is answered before and during a migration, so you know what changed and what broke.
LOT 16

Appendix · Why it hurts today

Three costs, every time you check

1

Build the comparison

A script or harness written for this migration, then thrown away.

2

Wade through noise

Timestamps, generated IDs, list order and whitespace differ on every call. A renamed field shows up as one field missing and another added.

3

Judge intent by hand

Each remaining difference is checked against the change list in someone's head. None of the tools we found does this step.

Petstore v2 to v3: 3 findings to read across 20 endpoints. nParity took about 5 seconds. By hand we estimate about 2 hours not yet timed.

Measured: 3 findings (1 unsure, 2 intended) and 5.0 s, from the saved Petstore run (20 endpoints on the contract, 5 with live calls). An earlier run without the intent note about separate databases reported 39 differences, most of them data. Estimated, not timed: about 2 hours by hand (20 endpoints x 3 samples x 2 minutes per comparison, the model used in the problem definition). A timed manual baseline is still to do. Step 3, judging intent, is the part no tool we found automates.
