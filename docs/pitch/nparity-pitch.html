LOT 02

Value proposition

What

From the first prototype to the day after cutover, nParity tells the backend engineer which differences between the old and new API are regressions, with a probability and a one-line reason for each.

Why

Today the check happens once, by hand, near the end, when a regression costs the most to fix. Replay tools show what differs, not whether it was meant.

What changes

Regressions surface while the work is in flight. The engineer reviews only regressions and unsure items, and the engineering manager signs off on a short list with confidence attached.

Land this in the first minute. Every slide after this is evidence for it. Pause after "not whether it was meant".

LOT 04

When it pays off

Ask it before, during and after the project

Before

Scope the change

Run the old API against an early prototype. See what will differ before you commit to a plan, and write the intent note from it.

During

Catch drift early

Run it on every pull request. A regression shows up the day it is introduced, while it is cheap to fix.

After

Sign off, then keep checking

Hand the manager a short list at cutover. Keep the run in CI so the next change is checked too.

Same engine, same report, at every stage of the project.

This is why the question is "will we", not "did we". The value comes from asking early and often, not once at the end.
LOT 05

Why it hurts today

Three costs, every time you check

1

Build the comparison

A script or harness written for this migration, then thrown away.

2

Wade through noise

Timestamps, generated IDs, list order and whitespace differ on every call. A renamed field looks like everything changed.

3

Judge intent by hand

Each remaining difference is checked against the change list in someone's head. No tool does this step.

Engineers spend X hours per check going through N differences by hand, and the few regressions hide among noise and intended changes.

Fill X and N from the stopwatch run on Petstore v2 to v3 before we present. Step 3 is the part nobody automates.

LOT 07

How it works

Steep, strain, match, compare, taste

STEP 1 Steep

Send the same requests to the old and new API.

Built from the old API's OpenAPI spec and seed values.

STEP 2 Strain

Mask timestamps and generated IDs. Sort unordered lists.

Fixed rules. No model.

STEP 3 Match

Pair moved endpoints and renamed fields.

Rules first. The model only for leftovers.

STEP 4 Compare

Diff values and types for every JSON path.

Rounding, counts and pagination: never the model.

STEP 5 Taste

Label each difference intended, regression or unsure.

Against your intent note, with a probability.

In: two base URLs, two OpenAPI specs, one paragraph of intentOut: a short report in the terminal or the browser
Keep this quick. The point: the model only does the two jobs that need judgement, matching leftovers and tasting. Everything else is deterministic.

LOT 09

Why trust it

Every verdict shows how sure it is

A real probability

Each label is read from the model's token probabilities, not a confidence score it makes up.

Higher bars where mistakes cost more

p ≥ 0.95 to accept a mapping. p ≥ 0.98 to accept a difference as intended. Regressions are never dismissed automatically.

Numbers stay deterministic

Rounding, counts and pagination are caught by the differ. The model never judges them.

Scored on every run

Each run is checked against an answer key, and the score is on screen.

We tested before we built: 66 model calls for about US$0.006. Yes/no questions rejected correct renames (p = 0.0017), so nParity asks multiple-choice questions.

Anticipate "why trust the AI?". The thresholds are the answer: the costlier the mistake, the higher the bar.

  • Under US$0.01 in model fees

In scope

  • OpenAPI specs on both sides
  • Request and response behaviour
  • Before, during and after the project

Out of scope

  • Vendor swaps where the flow changes
  • Database side effects
  • UI
  • Performance
Read the targets as promises we test live. Out of scope is a choice, not a gap.
