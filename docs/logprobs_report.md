# Logprobs on Fireworks + DeepSeek Flash — test report

**Verdict up front: the logprob classifier approach works — but only with reasoning
explicitly disabled, and only for up to 5 candidate codes per call.**
With `max_tokens: 1` and reasoning at its default, you get the logprob of the first
*reasoning* token (`"We"`), `message.content` is `""`, and no answer code appears
anywhere. Turn reasoning off and the first token is exactly `"A"` at p ≈ 0.999.

Longer lists still work for *picking* the right option — 10 options: p(correct) 0.995–1.000;
30 options: 0.80–0.89 — but only 4–5 codes fit in `top_logprobs`, so you get a reliable
argmax, not a calibrated k-way distribution. **Do not try to recover the rest by re-asking
a trimmed shortlist: that degrades the answer badly (measured, §3).**

- Date of run: single session, `results.json` + `raw/` regenerated by `logprobs_test.py`
- Model tested: `accounts/fireworks/routers/deepseek-v4p1-flash-1017-us`
- Base URL: `https://us.api.fireworks.ai/inference/v1`
- Client: `openai==3.59.0` (OpenAI-compatible), Python 3.12.10 (asdf), 66 calls total, ≈ **$0.006** of spend
- Data: only the toy API-mapping prompt from the brief. No company data. The API key is
  read from `FIREWORKS_API_KEY` and is never printed or written to disk.

## 2. Exact working request parameters (E4)

Chat-completions, OpenAI SDK, verbatim from `logprobs_test.py`:

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://us.api.fireworks.ai/inference/v1",
    api_key=os.environ["FIREWORKS_API_KEY"],
)

resp = client.chat.completions.create(
    model="accounts/fireworks/routers/deepseek-v4p1-flash-1017-us",   # the -us router is mandatory
    messages=[
        {"role": "system", "content":
            "You map API endpoints between an old and a new version. "
            "Answer with only the letter of the best match. No other text."},
        {"role": "user", "content": USER_CHOICE},                     # the E4 prompt from the brief
    ],
    reasoning_effort="none",   # <-- without this you get reasoning tokens, not the answer
    temperature=0,
    max_tokens=1,
    logprobs=True,
    top_logprobs=5,            # 5 is the hard maximum
)

lp = resp.choices[0].logprobs.content[0]      # first generated token
lp.token                                      # "A"     (exactly, no leading space)
lp.logprob                                    # -0.00113316
[(t.token, t.logprob) for t in lp.top_logprobs]
# [('A', -0.00113316), ('E', -7.00113297), ('C', -9.62613297),
#  ('B', -9.75113297), ('Let', -10.12613297)]
```

## 3. Scaling past 5 options, measured (E12–E15)

Same toy endpoint question, longer option lists. `reasoning_effort="none"`, `temperature=0`,
`max_tokens=1`, `top_logprobs=5` throughout; the only thing that changes is the option list.
`p(correct)` is the softmax renormalised over the codes that actually showed up in
`top_logprobs`, so it is conditional on the visible set.

| setup | options | p(correct) by order | codes visible | mass on non-code tokens |
|---|---|---|---|---|
| E4, brief's 5 options | 5 | 0.999 | 4/5 (`D` censored) | 4e-5 |
| E13, codes `01`–`10` | 10 | **1.000** | 4/10 | — |
| E14, letters, correct in slot 1 / 5 / 10 | 10 | **0.9975 / 0.9994 / 0.9946** | 4/10 | 5e-6 – 1.4e-4 |
| E12, letters + one near-duplicate distractor, correct in slot 1 / 5 / 10 | 10 | 0.9971 / 0.9994 / **0.5275** | 4–5/10 | 2e-5 – 7e-4 |
| E8, correct + 29 distractors | 30 | 0.805 (0.892 on an earlier run) | 4–5/30 | — |

### 3.1 Ten options is fine — for picking a winner

With a clean distractor set the answer is stable and confident at every position, including
last (slot 10: 0.9946). Digit codes (`01`–`10`) are single tokens and come back bare like
letters, so `01`–`30` is a valid coding scheme for wider lists. But only 4 of the 10 codes
are in `top_logprobs`:

```
E14 order 1  top5 = A(-0.007) E(-5.007) D(-11.007) H(-11.882) C(-11.882)
             visible A,E,D,H -> p(correct)=0.9975, P(other 6 codes) < 1.4e-4
```

So: **ranking yes, full 10-way distribution no.** You can report `p(best) ≈ 1 - ε` plus a
floor for the other six, but you cannot report "p(option 7)" — it was never in the top 5.

### 3.2 Near-duplicate options break it (E12)

I deliberately included one option that is a literal near-copy of the old endpoint:
`GET /v2/customers/{customerId}  returns { id, fullName, email }` (the old endpoint is
`GET /customers/{id}` returning `fullName`). With that option present and the correct one in
slot 10, the model produced a dead heat:

```
D(-0.83)  J(-0.83)   <- identical logprobs, p = 0.436 each
I(-2.08)  G(-6.205)
```

It split between "same resource name, most fields" and "renamed resource, matching shape".
Across two runs this slot scored 0.4362 and 0.5271 — sometimes losing, sometimes winning.
With the same 10 slots and no near-duplicate (E14) it scored 0.9946. The failure is the
option set, not the position and not the logprobs.

### 3.3 Two-stage shortlist re-ask: measured, and it does not work (E12/E14/E15)

My first instinct was: take the 5 visible codes, re-ask those 5 as a fresh A–E question.
That fails. Re-asking the same candidates with fresh letters:

| source | stage-1 p(correct) | stage-2 p(correct) | stage-2 winner | combined |
|---|---|---|---|---|
| E14 order 1 | 0.9975 | 0.4371 | first shortlist entry | 0.437 |
| E14 order 2 | 0.9994 | 0.7310 | first shortlist entry | 0.731 |
| E14 order 3 | 0.9946 | 0.4258 | first shortlist entry | 0.426 |
| E12 order 1 | 0.9971 | 0.0793 | `None of these` | 0.079 |
| E12 order 2 | 0.9994 | 0.0012 | `None of these` | 0.001 |
| E12 order 3 | 0.5275 | 0.0216 | `None of these` | 0.022 |

The distribution is not stable under a change of option set: 0.998 in a 10-way list becomes
0.44 in a 4-way list, and in the E12 lists it collapses onto `None of these`. E15 isolates
the cause — `None of these` is a magnet once the alternatives are removed:

| option set | p(correct) |
|---|---|
| `{correct, None of these, list clients}` (3 options) | **0.499** (tie: both tokens at **-0.6952**) |
| `{correct, list clients}` (2 options) | 0.9999 |
| `{correct, None of these}` (2 options) | 0.9241 |

Trim the list, keep `None of these`, and the model reads the question as "do only these
exist?" — a different question with a different answer. A shortlist round trip is therefore
not a recovery mechanism; it is a second, easier-to-get-wrong classifier.

## 4. Gotchas

1. **Region gating comes first, model id second.** `GET /models` lists deployment ids
   (`accounts/fireworks/models/deepseek-v4p1-flash-1017`) that this account cannot call:
   `HTTP 403 region not allowed: the requested model has deployments outside your account's
   US data residency. Use a model served in the US, such as a Fireworks router whose name
   ends in -us or -us-fast.` Only `accounts/fireworks/routers/deepseek-v4p1-flash-1017-us`
   (newest) and `…-flash-us` (older) work; `…-1017-spot`, `…-flash-spot`,
   `spot-deepseek-v4-flash` and both bare `models/…` ids are blocked. `…-1017-ultrafast`
   works but is not US-pinned. The router resolves server-side — the response `model`
   field says `accounts/fireworks/models/deepseek-v4p1-flash-1017`.
2. **Reasoning is on by default and eats the whole budget.** `max_tokens: 1` returned
   `content: ""`, `finish_reason: "length"`, and one logprob entry: token `"We"`,
   `top_logprobs = ["We", "</think>", "Need", "Answer", "The"]`. `usage.completion_tokens_details.reasoning_tokens = 1`.
   So with reasoning on, `logprobs.content` covers **reasoning** tokens, not answer tokens,
   and there is no answer token at all.
3. **Only three of the five disable switches actually work.**
   ✅ `reasoning_effort: "none"` · ✅ `extra_body={"thinking": {"type": "disabled"}}` ·
   ✅ `extra_body={"chat_template_kwargs": {"thinking": false}}` —
   all three give `content: "A"`, `reasoning_content` absent, `reasoning_tokens: 0`.
   ❌ `reasoning_effort: "minimal"` and `"low"` still reason (60–79 reasoning chars).
   ❌ `{"reasoning": {"enabled": false}}` → `400 Extra inputs are not permitted, field: 'reasoning'`.
   ❌ `{"disable_thinking": true}` → `400 Extra inputs are not permitted, field: 'disable_thinking'`.
   ❌ A system prompt ("Do not think step by step. Output the letter immediately.") does
   **not** suppress it.
4. **`top_logprobs` caps at 5, so a k-option softmax is truncated for k > 5.** In E4 code
   `D` fell outside the top-5, so the renormalised distribution silently sums over 4 codes.
   Treat missing codes as "below the cutoff floor" (≤ e^logprob_of_5th), never as 0, and
   consider reporting `1 - Σ p(present)`. In E8 only 5 of 30 codes were visible.
   Raw error for oversized values: `400 top_logprobs must be between 0 and 5, got 10`.
5. **No leading space, in chat mode.** The chat token is `"A"`, `bytes: [65]`, `token_id: 35`.
   Bare `A`–`E` all appear as single tokens in `top_logprobs`, so no `" A"` variant hunting
   is needed here. Note the model also emits a trailing empty token `""` when it stops
   (an artifact of the SDK's decoding of the final offset) — index 0 is the answer.
6. **`/completions` disagrees with chat on whitespace.** The same prompt scored on
   `/completions` returns `" A"` (leading space, `p = 0.666`) instead of `"A"` (`p = 0.999`),
   and `top_logprobs` there contain `" E"`, `" I"`, `" The"`, `"<｜end▁of▁sentence｜>"`.
   Do not mix the two endpoints in one model of the world.
7. **`echo` is broken for prompt scoring.** `400 Prompt logprobs (echo or echo_last with
   logprobs) are temporarily unsupported for this model. Disable echo/echo_last or omit
   logprobs.` So the "score every candidate as a continuation" plan is not available as
   prompt-token logprobs; it can only be done by generating the continuation.
8. **`finish_reason` is `"length"` when `max_tokens: 1` truncates after a correct token.**
   Don't gate on `finish_reason == "stop"`; check `logprobs.content[0].token`.
9. **Not bitwise deterministic at temperature 0.** 5 identical E4 calls: same first token
   every time, 4 of 5 distributions byte-identical, worst-case p(A) spread 4.1e-4. More
   importantly the *membership* of `top_logprobs` flips — code `D` appeared in 1 of 5 runs.
   So a code can be absent from one run and present in the next: don't cache single-run
   distributions as canonical, and don't treat absence as a hard zero.
10. **Yes/no framing is actively wrong here.** `Is GET /v2/clients/{clientId} the same
    operation?` → `N` with p = 0.9983 (P(Y) = 0.0017), because `fullName`/`legacyCode` were
    renamed/dropped. The same content under "which is the *best match*" → `A` at 0.999.
    The binary question asks about identity, the A–E question asks about ranking; the model
    answers accordingly.
11. **`reasoning_content` is absent, not `null`, when reasoning is off** — use
    `msg.get("reasoning_content")`, not attribute access.
12. Response carries Fireworks-only extras per token (`sampling_logprob`, `token_id`,
    `text_offset`, plus always-null `routing_matrix`/`last_activation`/`sampling_mask*`/
    `extra_*`). Ignore them unless you want the sampling-vs-computed logprob split.
13. **Probabilities are conditional on the option list, not just the answer.** The same
    candidate scored 0.998 in a 10-option list and 0.44 in a 4-option list (E14, E15), and
    a trimmed list containing `None of these` pulls the mass onto it (E15: exact tie at
    -0.6952). Never mix logprobs collected from prompts with different option sets, and
    never compare a k-way probability to a 5-way one.
14. **A near-duplicate option can produce an exact tie.** E12 slot 10:
    `D(-0.83)` and `J(-0.83)`, identical to 2 decimals. If two options can both be read as
    "the same operation", the distribution splits between them and `argmax` becomes a coin
    flip — dedupe the candidate set before asking.
15. **`None of these` is not a neutral class.** It absorbs roughly half the mass as soon as
    the competing options are removed, and can win outright (E12 stage 2). Treat it as a
    "no confident match" escape hatch and expect it to interact with list length.

## 5. Recommendation

**Use the logprob approach — it is viable on this model, with three hard constraints.**

What it gives you: a per-option probability that is well-calibrated enough to be useful,
stable under option reordering (E6: correct option won in all 3 orders, 0.998/0.999/0.999,
no slot-A bias), and cheap (159 prompt + 1 completion token, ≈ $0.00007 per call, 0.6 s).
It also survives long option lists for *selection*: 10 options 0.995–1.000 (E14), 30 options
0.80–0.89 (E8), including when the right answer sits last in the list.

Three hard constraints, in order of how much they change the design:

1. **Reasoning must be off** (`reasoning_effort="none"`). Otherwise there is no answer token
   at `max_tokens: 1` — you get a truncated thinking prefix instead.
2. **At most 5 codes per call.** `top_logprobs` max is 5, so a distribution over more than
   5 options is censored: you learn the top-5 and a floor for the rest. `P(option 17)` is
   simply unobtainable from a single call.
3. **The probability is conditional on the option list you showed.** Change the list and the
   number changes (E14/E15: 0.998 → 0.44 for the same candidate). This is the constraint that
   kills the obvious workaround for (2).

Practical recipe:

- **k ≤ 5 options** → single call as in §2, softmax over the codes you find, report the
  censored remainder explicitly. This is the calibrated case and the only one where the
  number means what it looks like.
- **5 < k ≤ ~30 options** → still a *single* call with all k options, and use it as a
  **ranker, not a probability engine**: take `argmax` over the visible codes, report
  `p(winner)` as "≈1, at least 1 - ε", and add the censored remainder as a floor. Do not
  renormalise into a full k-way distribution and present it as calibrated.
- **Do not re-ask a trimmed shortlist** (§3.3). Measured 0.998 → 0.001–0.73, and with
  `None of these` still in the list it becomes the winner. If you need a real k-way
  distribution with k > 5, sample instead.
- **Need a full distribution for k > 5** → sample-and-vote: `n = 8..16` completions at
  `temperature ≈ 0.7`, same 1-token answer, count votes. Loses the probability scale, keeps
  the ranking; ≈ $0.001 per question at these prices. Vote spread at least degrades
  gracefully, unlike a shortlist re-ask.
- **Dedupe the candidate set first.** Near-duplicate options produce exact ties (E12:
  -0.83 vs -0.83) and a coin-flip `argmax`. Collapse options that share resource + field
  signature before asking, or keep them and accept a two-way split.

What to avoid:

- **Don't use the yes/no formulation** (E5). It collapses to "not identical → N" and gives
  P(Y) ≈ 0 for a correct match. If you need a binary decision, derive it from the
  multi-option distribution (p(best) vs p(none-of-these)).
- **Don't lean on `None of these`.** It is an escape hatch that soaks up mass whenever the
  other options are trimmed (E15), so its probability is not comparable across list lengths.
- **Don't use ranked JSON with self-reported scores as the fallback** — the same model,
  when asked for `{"label","reason"}` in JSON mode (E9), returns the right label but its
  *reason* text is where the nuance lives, and self-reported numeric confidence from a
  reasoning model is unbounded and uncalibrated. The logprob or the vote count is strictly
  better evidence.
- **JSON mode is fine if you want reasons**, and the label logprob is recoverable
  (token index 3 after `{"label":"`), but it costs ~33–36 output tokens versus 1 and it
  constrains the sampled token set, so probabilities are grammar-conditioned and not
  directly comparable with plain-mode probabilities (E9: 0.952/0.914 vs 0.999).
